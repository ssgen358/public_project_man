## 1. 本資料の目的と使い方

### 1.1 目的

本資料は、テスト設計時に「何を確認すべきか（テスト観点）」を網羅的に整理した一覧である。

テストケースを作成する際に**観点の抜け漏れを防ぐチェックリスト**として活用することを主な目的とする。観点を洗い出してからテストケースに落とし込むことで、以下の効果が得られる。

- 担当者・工程によるテスト品質のバラツキを抑制できる
- 「なんとなく思いついたものだけテストする」属人的な設計を避けられる
- レビュー時に「この観点は？」という議論の出発点になる

### 1.2 使い方

**テストケース設計時**:
1. テスト対象の機能・処理を確認する
2. 本資料から該当するテスト工程の観点一覧を開く
3. 各観点について「この機能ではテストが必要か？」を判断する
4. 必要と判断した観点に対してテストケースを起こす
5. 不要と判断した観点には理由を残しておく（「帳票機能なし → 帳票観点はスキップ」等）

**テスト仕様書レビュー時**:
- 本資料の観点チェックリスト（付録）と照らし合わせ、テストケースの抜け漏れを確認する

> [!NOTE]
> 本資料に記載された全観点を全機能でテストする必要はない。機能の特性・リスク・プロジェクトのコスト制約に応じて取捨選択する。ただし取捨選択した根拠は記録しておくこと。

> [!WARNING]
> テスト観点の抜け漏れで最もリスクが高いのは「正常系しか確認しない」パターン。異常系・境界値・権限制御はテストケース数を意識的に増やさないと抜けやすい。本資料の観点カテゴリを必ず一巡すること。

## 2. テスト工程と観点の全体像

### 2.1 各工程で「何を」「誰が」確認するか

| 工程 | 主な確認対象 | 実施主体 | 本資料の参照章 |
| :--- | :--- | :--- | :--- |
| **単体テスト** | 個別モジュール・関数・クラスの内部ロジック | 開発担当者 | 3章 |
| **結合テスト** | モジュール間・画面間・システム間の連携動作 | テスト担当者（開発側） | 4章 |
| **総合テスト** | システム全体の機能・非機能（性能・セキュリティ等） | テスト担当者（開発側） | 5章 |
| **受入テスト（UAT）** | 業務要件の充足・ユーザー操作観点 | ユーザー担当者 | ※本資料スコープ外 |

### 2.2 工程と観点のカバレッジ俯瞰図

各テスト工程で主にカバーする観点領域を示す。

```
観点カテゴリ             │ UT │ IT │ ST │
─────────────────────────┼────┼────┼────┤
内部ロジック・演算        │ ◎  │    │    │
条件分岐・ループ          │ ◎  │    │    │
例外処理・エラーハンドリング│ ◎  │ ○  │    │
入力バリデーション        │ ○  │ ◎  │ ○  │
画面遷移・業務フロー      │    │ ◎  │ ◎  │
データ連携（DB・API）      │    │ ◎  │ ○  │
認証・認可・権限制御      │    │ ◎  │ ◎  │
外部システム連携          │    │ ◎  │ ○  │
業務シナリオ（エンドツーエンド）│  │ ○  │ ◎  │
性能・負荷                │    │    │ ◎  │
セキュリティ              │ ○  │ ○  │ ◎  │
ブラウザ互換性・UI        │    │ ○  │ ◎  │
運用・監視・ログ          │    │    │ ◎  │
データ移行                │    │    │ ◎  │

凡例: ◎ 主担当  ○ 補完的に確認  （空白）基本対象外
```

### 2.3 観点の引き継ぎ方針

上流工程でカバーした観点は、下流工程では「全件再実施」ではなく「代表的な正常系 + 回帰確認」に絞るのが効率的。

| 状況 | 対応方針 |
| :--- | :--- |
| 単体テストでカバー済みの内部ロジック | 結合テストでは代表ケースのみ確認（全分岐は再実施しない） |
| 結合テストでカバー済みの機能正常系 | 総合テストではシナリオ観点でのみ再確認 |
| バグ修正箇所 | 該当観点の再テスト（回帰テスト）を必ず実施 |

## 3. 単体テストの観点

単体テスト（Unit Test）は、個別のモジュール・関数・クラスを**他のコンポーネントから切り離した状態**で検証する。「コードが仕様通りに動くか」を開発者が自ら確認するフェーズ。

### 3.1 正常系ロジック

| 観点 | 確認内容 | 具体例 |
| :--- | :--- | :--- |
| **基本動作** | 正しい入力値で期待する出力・戻り値が返るか | 引数に `10` を渡すと `100`（×10処理）が返る |
| **計算精度** | 四則演算・丸め処理・浮動小数点の精度 | 消費税計算で小数点以下が正しく切り捨て/四捨五入されるか |
| **文字列処理** | 結合・分割・整形・トリミングが正確か | 氏名の姓名を結合した結果が期待通りか |
| **日付・時刻処理** | 日付計算・フォーマット変換・タイムゾーン対応 | 「2026/01/31 + 1ヶ月」が「2026/02/28」になるか |
| **型変換** | 型キャスト・パースが正確か | 文字列 `"123"` を数値 `123` に正しく変換できるか |
| **コレクション操作** | リスト・配列のソート・フィルタ・集計が正確か | 売上リストを降順ソートした結果が正しいか |

### 3.2 異常系・例外処理

| 観点 | 確認内容 | 具体例 |
| :--- | :--- | :--- |
| **NULL/空値の扱い** | NULL・空文字・空リストを渡した時の動作 | NULL渡しでNullPointerExceptionではなくカスタム例外が返るか |
| **型不一致** | 想定外の型を渡した時の動作 | 数値を期待するメソッドに文字列を渡した場合 |
| **例外の発生・捕捉** | 例外が正しいタイミングで発生し、適切にキャッチされるか | DB接続エラー発生時に適切なカスタム例外がスローされるか |
| **例外メッセージ** | 例外発生時のメッセージ・エラーコードが仕様通りか | エラーコード `E001` と対応メッセージが返るか |
| **ロールバック** | 例外発生時にトランザクションが正しくロールバックされるか | 処理途中で例外発生 → DBに中途半端なデータが残らないか |
| **リソース解放** | 例外発生時にファイル・コネクション等が適切にクローズされるか | finally / using / try-with-resourcesが機能しているか |

### 3.3 境界値・入力範囲

| 観点 | 確認内容 | 具体例 |
| :--- | :--- | :--- |
| **数値の上限** | 上限値・上限+1・上限-1での動作 | 最大値 `999` → OK / `1000` → エラー / `998` → OK |
| **数値の下限** | 下限値・下限-1・下限+1での動作 | 最小値 `1` → OK / `0` → エラー / `2` → OK |
| **文字数制限** | 最大文字数・最大+1文字・0文字での動作 | 50文字 → OK / 51文字 → エラー / 0文字（空） → エラー |
| **日付の範囲** | 有効な日付範囲の境界値 | 1900/01/01（下限）/ 9999/12/31（上限）/ 2月末（うるう年） |
| **ゼロ・負数** | 0・負数が有効値として処理されるか（またはエラーか） | 数量 `0` は許可するか / `-1` はエラーにするか |
| **最大桁数** | 最大桁数を超えた場合の動作 | 10桁の整数を処理するメソッドに11桁を渡した場合 |

### 3.4 条件分岐

| 観点 | 確認内容 | 具体例 |
| :--- | :--- | :--- |
| **全分岐パターン** | if/switch文の全ての分岐が実行されるか | `if (a > 0)` の `true` / `false` 両方を確認 |
| **複合条件** | AND/ORの組み合わせが正しく評価されるか | `A && B` のAのみtrue / BのみtrueのケースもカバーするOK |
| **デフォルト処理** | switch文のdefaultケース、else句が正しく動作するか | 想定外の値を渡した時にデフォルト処理が実行されるか |
| **早期リターン** | ガード節（早期return）が意図した条件で発動するか | バリデーション失敗時に即returnが行われているか |
| **フラグ反転** | boolean値の切り替えが正しく動作するか | `isEnabled = !isEnabled` の前後の状態が正しいか |

### 3.5 ループ処理

| 観点 | 確認内容 | 具体例 |
| :--- | :--- | :--- |
| **0件（空のコレクション）** | 処理対象が0件の場合に正常終了するか | 空リストを渡してもエラーにならず、空の結果を返すか |
| **1件** | 最小ケース（1件）で正しく動作するか | 要素が1件のリストで正常に処理が完了するか |
| **大量件数** | 大量データで正しく動作するか（性能・メモリは別途） | 1万件のリストで処理が正常完了するか |
| **ループ継続条件** | ループが期待する回数だけ実行されるか | while/forのカウンタ・条件が正確か |
| **途中終了** | break/continueが意図した条件で発動するか | 特定条件でループを抜ける処理が正しく機能するか |
| **累積・集計処理** | ループ内の累積計算が正しいか | 合計金額の加算が正確か（初期値・加算順序） |

### 3.6 データ変換・マッピング

| 観点 | 確認内容 | 具体例 |
| :--- | :--- | :--- |
| **エンティティ変換** | DTOとEntityの相互変換で項目の欠落・マッピング誤りがないか | UserEntity → UserDTO変換で全フィールドが正しく写っているか |
| **フォーマット変換** | 日付・数値のフォーマット変換が正確か | `20260225` → `2026/02/25` の変換が正しいか |
| **文字コード変換** | 文字コード変換で文字化けが発生しないか | UTF-8 → Shift-JIS変換で特殊文字（①②等）が正しく変換されるか |
| **コード変換** | コード値（数値）から名称（文字列）への変換が正しいか | `1` → `有効` / `0` → `無効` のマッピングが正しいか |

### 3.7 コードカバレッジ

| 観点 | 確認内容 | 目標値（参考） |
| :--- | :--- | :--- |
| **行カバレッジ（Line Coverage）** | テストで実行されたコード行の割合 | 80%以上（プロジェクト方針による） |
| **分岐カバレッジ（Branch Coverage）** | if/switch等の全分岐がテストされているか | 70%以上（プロジェクト方針による） |
| **条件カバレッジ（Condition Coverage）** | 複合条件の全組み合わせがテストされているか | 重要モジュールで適用 |
| **未到達コード** | 到達不能なコード（デッドコード）が存在しないか | 0件を目指す |

> [!TIP]
> カバレッジ数値を目標にすると「カバレッジを上げるためだけの意味のないテスト」が増える。カバレッジは「テストの抜け漏れ検出ツール」として使い、低いカバレッジの箇所に観点の漏れがないかを確認する目的で活用する。

### 3.8 非同期処理・並行処理

| 観点 | 確認内容 | 具体例 |
| :--- | :--- | :--- |
| **非同期の完了タイミング** | 非同期処理の完了を正しく待機しているか | Promiseのresolve/rejectが正しく処理されるか |
| **エラーハンドリング（非同期）** | 非同期処理のエラーが適切にキャッチされるか | async/awaitのtry-catchが機能しているか |
| **並行処理の競合** | 複数スレッドが同一リソースを操作する際の競合 | 共有変数へのアクセスが排他制御されているか |
| **タイムアウト** | 処理タイムアウト時に適切に処理が中断されるか | 設定秒数で処理が中断しエラーが返るか |

### 3.9 外部依存のモック・スタブ化

| 観点 | 確認内容 |
| :--- | :--- |
| **モック戻り値の確認** | モックが期待する値を返した時にロジックが正しく動作するか |
| **モックエラー時の動作** | 外部サービス（DB・API）がエラーを返した時の動作確認 |
| **モック呼び出し回数** | 外部依存が期待する回数だけ呼ばれているか（余計な呼び出しがないか）|

## 4. 結合テストの観点

結合テスト（Integration Test）は、単体テストで確認済みのモジュールを組み合わせ、**インターフェースとデータ連携**が正しく動作することを確認するフェーズ。

### 4.1 画面遷移・ナビゲーション

| 観点 | 確認内容 | 具体例 |
| :--- | :--- | :--- |
| **正常遷移** | 操作後に意図した画面へ遷移するか | 「登録」ボタン押下 → 登録完了画面または一覧画面へ遷移する |
| **キャンセル・戻る** | キャンセル・ブラウザの「戻る」ボタンで正しく前画面に戻るか | 入力途中でキャンセル → 入力内容が破棄されて前画面に戻る |
| **エラー時の遷移** | バリデーションエラー・処理エラー時の遷移先が正しいか | 必須未入力エラー → 同画面にとどまりエラーメッセージを表示 |
| **直接URLアクセス** | ログインせずにURLを直打ちした場合にログイン画面へリダイレクトされるか | 認証なしでURLアクセス → `/login` にリダイレクト |
| **権限外URLアクセス** | 権限のない画面のURLを直打ちした場合に弾かれるか | 一般ユーザーが管理画面URLを直打ち → 403またはリダイレクト |
| **遷移時のデータ引き継ぎ** | 前画面の値・選択内容が遷移先に正しく引き継がれているか | 一覧画面で選択したレコードのIDが詳細画面に渡っているか |
| **タブ・ウィンドウ操作** | 複数タブでの操作が互いに干渉しないか | 別タブで別ユーザーとしてログインした場合の動作 |

### 4.2 入力バリデーション

| 観点 | 確認内容 | 具体例 |
| :--- | :--- | :--- |
| **必須チェック** | 必須項目が未入力の場合にエラーメッセージが表示されるか | 名前（必須）が空のまま送信 → 「名前を入力してください」 |
| **形式チェック** | メールアドレス・電話番号・日付など形式が正しいか | `abc` をメールアドレスに入力 → 形式エラー |
| **文字種チェック** | 半角/全角・英数字のみ等の制約が機能するか | 半角数字のみ許可フィールドに全角数字を入力 |
| **文字数チェック** | 最大・最小文字数の制約が機能するか | 50文字制限フィールドに51文字入力 → エラー |
| **数値範囲チェック** | 数値の上限・下限・0・負数の制約が機能するか | 年齢フィールドに `-1` や `200` を入力 |
| **日付整合性チェック** | 開始日＜終了日のような項目間の整合性 | 終了日が開始日より前 → エラー |
| **重複チェック** | 一意制約があるキー項目の重複登録がエラーになるか | 既存のメールアドレスで新規登録 → 「既に登録済みです」 |
| **特殊文字の扱い** | `<`, `>`, `"`, `'`, `&`, `%` 等の特殊文字が入力できるか（または制限されるか） | 商品名に `<script>` を入力した場合の挙動 |
| **エラー表示位置・内容** | エラーメッセージが該当項目の近くに表示されるか / 内容が分かりやすいか | エラーがフォームの最上部にまとめて出るか、各項目横に出るか |
| **複数エラーの同時表示** | 複数項目にエラーがある場合に全件同時に表示されるか | 必須チェックが3項目同時にエラー → 3件分のメッセージが表示 |

> [!TIP]
> バリデーションのテストで見落とされやすいのは「前後のスペース（トリミング）」の扱い。半角スペースのみの入力が必須チェックを通過してしまう実装上の不備はよく発生する。各必須項目でスペースのみ入力のケースを確認する。

### 4.3 データ連携（画面⇔DB）

| 観点 | 確認内容 | 具体例 |
| :--- | :--- | :--- |
| **登録（INSERT）** | 画面入力値が全項目DBに正確に保存されるか | 登録後にDBの該当レコードをSELECTして全フィールド突合 |
| **参照（SELECT）** | DB上のデータが画面に正確に表示されるか | DBのデータを直接書き換えた後、画面の表示が変わっているか |
| **更新（UPDATE）** | 変更した値のみが更新され、他フィールドに影響がないか | 1項目だけ変更 → 変更フィールドのみ更新され他は元の値のまま |
| **削除（DELETE）** | 削除後に該当レコードが参照不能になるか | 削除後に詳細画面を開くとエラーまたは「削除済み」表示 |
| **自動設定項目** | 登録日時・更新日時・登録者・更新者が自動設定されるか | 登録後にDBで `created_at` / `updated_at` を確認 |
| **NULL保存** | 任意項目を未入力で登録した場合にNULLが保存されるか | 任意フィールドを空で登録 → DBにNULL保存 |
| **件数・一覧整合** | 一覧画面の件数とDBの件数が一致しているか | DBに10件 → 一覧に10件表示 |
| **ページング時の整合性** | ページングでデータの抜け・重複がないか | 全ページを合計した件数がDB件数と一致するか |

### 4.4 認証・セッション管理

| 観点 | 確認内容 | 具体例 |
| :--- | :--- | :--- |
| **ログイン（正常）** | 正しいID・パスワードでログインできるか | 登録済みユーザーでログイン → ホーム画面遷移 |
| **ログイン（異常）** | 誤ったパスワードでログインできないか | 誤パスワード → エラーメッセージ表示、ログイン拒否 |
| **ログインエラー回数制限** | 一定回数失敗でアカウントロックされるか | 5回失敗 → ロックメッセージ表示、ログイン不可 |
| **ログアウト** | ログアウト後にセッションが無効化されるか | ログアウト後に「戻る」ボタンで戻れないか |
| **セッションタイムアウト** | セッション有効期限切れ後に操作した場合にログイン画面へ遷移するか | 一定時間操作なし → タイムアウト → ログイン画面 |
| **タイムアウト後の送信** | セッション切れ後に送信ボタンを押した場合に適切に処理されるか | タイムアウト後の送信 → エラーメッセージ（データが2重登録されない） |
| **パスワードの平文保存確認** | パスワードがDBにハッシュ化されて保存されているか | DBのpasswordカラムがハッシュ値になっているか |

### 4.5 権限・アクセス制御

| 観点 | 確認内容 | 具体例 |
| :--- | :--- | :--- |
| **ロール別画面表示** | ロールに応じて画面・メニューの表示/非表示が正しいか | 一般ユーザーには「管理メニュー」が非表示 |
| **ロール別操作制限** | ロールに応じてボタン・リンクの活性/非活性が正しいか | 閲覧権限のみのユーザーには「編集」「削除」ボタンが非活性 |
| **ロール別データ表示** | 参照可能なデータがロールに応じて絞り込まれているか | 担当者は自分が担当するデータのみ表示 |
| **他ユーザーのデータへのアクセス** | URLのIDを変えて他ユーザーのデータにアクセスできないか | `/user/100/edit` のIDを `101` に変更してアクセス → 403 |
| **権限昇格の試み** | APIリクエストを直接操作して権限外の操作ができないか | 一般ユーザーが管理者向けAPIをcurlで直接呼び出した場合 |

> [!WARNING]
> フロント（画面側）でボタンを非表示にしていても、APIを直接呼び出せば操作できてしまうケースは非常に多い。「画面で見えないから安全」ではなく、バックエンドAPI側でも権限チェックを実装・確認することが必須。

### 4.6 API・内部インターフェース

| 観点 | 確認内容 | 具体例 |
| :--- | :--- | :--- |
| **リクエスト仕様の一致** | APIのリクエストパラメータが仕様書と一致しているか | 必須パラメータ・型・名称が仕様書通りか |
| **レスポンス仕様の一致** | APIのレスポンスのフィールド・型・値が仕様書と一致しているか | JSONのフィールド名・型・ネスト構造が仕様通りか |
| **ステータスコード** | 正常時・異常時のHTTPステータスコードが仕様通りか | 正常: 200 / 登録: 201 / バリデーションエラー: 400 / 未認証: 401 / 権限なし: 403 / 未存在: 404 |
| **エラーレスポンス形式** | エラー時のレスポンスにエラーコード・メッセージが含まれるか | `{"error": {"code": "E001", "message": "..."}}` の形式確認 |
| **必須パラメータ省略** | 必須パラメータを省略した場合に400エラーが返るか | 必須フィールドなしで呼び出し → 400 Bad Request |
| **余分なパラメータの無視** | 仕様外のパラメータを送っても正常動作するか（または適切にエラーか） | 仕様にないフィールドを追加送信 → 無視されるか400か |
| **Content-Type** | リクエスト・レスポンスのContent-Typeが正しいか | `application/json` が設定されているか |

### 4.7 外部システム連携

| 観点 | 確認内容 | 具体例 |
| :--- | :--- | :--- |
| **正常連携** | 外部システムへのリクエスト送信・レスポンス受信が仕様通りか | 外部APIに正しいデータが送られ、レスポンスが正しく処理されるか |
| **外部エラー時の動作** | 外部システムがエラーを返した場合に適切に処理されるか | 外部APIが500エラー → 画面に「しばらくしてから再試行してください」と表示 |
| **タイムアウト** | 外部システムが無応答の場合にタイムアウト処理が機能するか | 設定秒数で処理を中断しエラーを返すか |
| **リトライ処理** | 外部エラー時にリトライが仕様通りの回数実行されるか | 3回リトライ後に最終エラーを返すか |
| **ファイル連携（送信）** | 生成したファイルのフォーマット・文字コード・改行コードが仕様通りか | CSVの区切り文字・囲み文字・ヘッダー行の有無 |
| **ファイル連携（受信）** | 受信したファイルのデータを正しく取り込めるか | 仕様通りのCSVを取り込み → DBに正しく登録されるか |
| **ファイル連携（異常）** | 不正なフォーマット・文字化けのファイルを受信した場合の動作 | フォーマット違反のCSV → エラーログを出力し処理を中断 |

### 4.8 バッチ処理

| 観点 | 確認内容 | 具体例 |
| :--- | :--- | :--- |
| **正常終了** | バッチが正常終了し、期待するデータが生成・更新されているか | バッチ実行後のDBデータ件数・内容の確認 |
| **処理件数の確認** | バッチログに処理件数が記録され、実際の処理件数と一致するか | ログ「処理100件」 = DB更新100件 |
| **0件データ** | 処理対象が0件の場合にエラーなく正常終了するか | 処理対象データなし → エラーなし、ログに「0件処理」 |
| **異常終了・ロールバック** | バッチ途中でエラーが発生した場合にロールバックされるか | 50件目でエラー → 1〜49件の変更がロールバックされているか |
| **重複実行の防止** | 同一バッチが二重起動されないか（排他制御） | 実行中に同じバッチを起動 → 拒否またはキュー待機 |
| **べき等性** | 同じバッチを複数回実行しても同じ結果になるか | 2回実行してもデータが重複登録されないか |
| **実行ログ** | バッチの開始・終了・エラーがログに記録されているか | ログファイルに開始時刻・終了時刻・処理件数・エラー内容が出力されるか |

### 4.9 トランザクション制御

| 観点 | 確認内容 | 具体例 |
| :--- | :--- | :--- |
| **コミット** | 全処理が正常完了した場合にコミットされるか | 登録→更新の2テーブル操作が全てコミットされているか |
| **ロールバック（業務エラー）** | 業務ロジックエラー時にロールバックされるか | バリデーションエラーで画面に戻った際に不完全なDBデータが残らないか |
| **ロールバック（システムエラー）** | 予期せぬ例外発生時にロールバックされるか | 例外スロー → コミット前の状態に戻るか |
| **楽観的ロック** | 同一データを複数ユーザーが同時更新しようとした場合に後者が弾かれるか | ユーザーAとBが同じレコードを同時に編集 → 後から更新したBにエラー |
| **悲観的ロック** | ロック取得中は他のプロセスがアクセスできないか | SELECT FOR UPDATE で取得したレコードへの別接続からのアクセス |
| **デッドロック** | デッドロックが発生するシナリオを実施し適切にハンドリングされるか | 相互参照する2テーブルへの同時更新 → デッドロック検出・エラー返却 |

## 5. 総合テストの観点

総合テスト（System Test）は、システム全体が業務要件・非機能要件を満たしているかを確認するフェーズ。結合テストで確認したモジュール連携をベースに、より広い視点での確認を行う。

### 5.1 業務フロー（エンドツーエンド）

| 観点 | 確認内容 | 具体例 |
| :--- | :--- | :--- |
| **主要業務シナリオ** | ユーザーが実際に行う代表的な業務フローが一連で完結するか | 「申請→承認→通知→完了」の一連フローが正常動作するか |
| **業務間連携** | 複数業務間でデータが正しく引き継がれるか | 受注データが自動的に在庫に反映され、出荷指示に連携されるか |
| **ロール間連携** | 複数ロールのユーザーが協調して行う業務フロー | 一般ユーザーが申請 → 管理者が承認 → 完了通知が届くフロー |
| **例外業務フロー** | 差し戻し・取り消し・修正などの例外的な業務フロー | 承認済みデータの取り消し → 申請者への差し戻し通知 |
| **業務ルールの遵守** | システムが業務上のルールを強制しているか | 残高不足での決済を不可にする / 二重申請を防止する |

### 5.2 性能テスト

| 観点 | 確認内容 | 目標値（例） |
| :--- | :--- | :--- |
| **レスポンスタイム** | 通常負荷時のレスポンスが目標値以内か | 95パーセンタイルで3秒以内 |
| **スループット** | 単位時間あたりの処理件数が目標値以上か | 100トランザクション/秒以上 |
| **同時接続数** | 想定ピーク時の同時接続ユーザー数で性能が維持されるか | 200同時接続でレスポンスタイム目標値を達成 |
| **大量データ参照** | 大量データが存在する環境での一覧表示・検索のレスポンス | 100万件のDBでの検索が5秒以内 |
| **繰り返し実行** | 長時間稼働でメモリリーク・性能劣化が発生しないか | 8時間連続稼働後も初期と同等のレスポンス |

> [!NOTE]
> 性能テストはプロジェクト規模・システム特性によって実施範囲を判断する。小規模システムでは「代表的な重い処理のレスポンスタイム確認」程度に留め、大規模・高トラフィックシステムでは JMeter 等の負荷テストツールを使った本格的な性能テストを計画する。

### 5.3 負荷テスト・ストレステスト

| 観点 | 確認内容 | 確認ポイント |
| :--- | :--- | :--- |
| **高負荷時の動作** | 想定ピークの1.5〜2倍の負荷をかけた場合に安定して動作するか | エラー率・レスポンスタイムの変化 |
| **限界負荷** | どの負荷レベルからシステムが不安定になるか | レスポンスタイムの急増・エラー発生開始ポイント |
| **負荷後の回復** | 高負荷が落ち着いた後に正常なレスポンスに戻るか | 負荷テスト終了後のレスポンスタイム回復 |
| **ディスク使用量** | 長期稼働でログ・一時ファイルによるディスク枯渇が発生しないか | ログローテーション・一時ファイルの削除が機能しているか |
| **コネクションプール** | DB接続の枯渇が発生しないか | 高負荷時にDBコネクション数が上限に達しないか |

### 5.4 セキュリティテスト

| 観点 | 確認内容 | 確認方法 |
| :--- | :--- | :--- |
| **SQLインジェクション** | SQLインジェクション攻撃によってDBが不正操作されないか | 入力フィールドに `' OR '1'='1` 等を入力して確認 |
| **XSS（クロスサイトスクリプティング）** | 悪意あるスクリプトが画面に実行されないか | `<script>alert('XSS')</script>` を入力して確認 |
| **CSRF（クロスサイトリクエストフォージェリ）** | 外部サイトからの不正なリクエストを受け付けないか | CSRFトークンが実装されているか / ヘッダーチェック |
| **ディレクトリトラバーサル** | ファイルパスを操作して非公開ファイルにアクセスできないか | `../../../etc/passwd` 等を入力フィールドに指定 |
| **クリックジャッキング** | iframeで埋め込まれた画面から操作できないか | `X-Frame-Options` ヘッダーの確認 |
| **セッション固定攻撃** | ログイン後にセッションIDが再生成されるか | ログイン前後のセッションIDを比較 |
| **通信の暗号化（HTTPS）** | 本番環境で全通信がHTTPS通信になっているか | HTTP接続時にHTTPSにリダイレクトされるか |
| **HTTPヘッダーのセキュリティ設定** | セキュリティ関連HTTPヘッダーが設定されているか | `Strict-Transport-Security`, `Content-Security-Policy` 等 |
| **パスワードポリシー** | 推測されにくいパスワード設定が強制されているか | 脆弱なパスワード（`password123`）で登録できないか |
| **パスワードのハッシュ化** | DBにパスワードが平文保存されていないか | DBのパスワードカラムがハッシュ値か |
| **不要なポート・サービスの公開** | 不要なポートが外部に公開されていないか | ポートスキャンで不要なポートが開いていないか |
| **エラーメッセージの情報漏洩** | エラーメッセージにスタックトレース等の内部情報が露出しないか | エラー発生時の画面表示にSQL文・ファイルパスが含まれないか |

> [!TIP]
> セキュリティテストは専門知識が必要な項目が多い。プロジェクト内での実施が難しい場合は、脆弱性診断ツール（OWASP ZAP等）の導入、または外部の脆弱性診断サービスの活用を検討する。少なくとも「OWASP Top 10」の主要項目だけでも確認しておくことを推奨する。

### 5.10 バックアップ・リストア・災害対策

| 観点 | 確認内容 | 確認方法 |
| :--- | :--- | :--- |
| **バックアップの取得** | 定期バックアップが設定通りに取得されているか | バックアップファイルの存在・更新日時を確認 |
| **バックアップの完全性** | バックアップファイルが破損なく取得されているか | バックアップファイルの整合性チェック（MD5等） |
| **リストアの実施** | バックアップからのリストアが正常に完了するか | テスト環境でリストアを実施し、データが復元されるか |
| **リストア時間** | リストアにかかる時間が業務継続性の要件を満たすか | RTO（目標復旧時間）内にリストアが完了するか |
| **フェールオーバー** | 冗長構成の場合に切り替えが自動で行われるか | プライマリサーバーを停止 → スタンバイに自動切り替え |

### 5.11 データ移行

> [!NOTE]
> データ移行は新規システム導入時・既存システムからの乗り換え時に特有のテスト項目。新規構築のみで移行がない場合はスキップ。

| 観点 | 確認内容 | 確認方法 |
| :--- | :--- | :--- |
| **移行データ件数の一致** | 旧システムのデータ件数と移行後のデータ件数が一致するか | 旧DB件数 = 新DB件数の突合 |
| **移行データの内容確認** | 移行後のデータが旧システムの値と一致するか（全件または抽出確認） | サンプリングしてフィールドごとに突合 |
| **データ変換の正確性** | コード変換・形式変換が仕様通りに行われているか | 旧システムのコード `1` → 新システムのコード `A` に変換されているか |
| **移行後の業務動作** | 移行データで業務システムが正常に動作するか | 移行データを使って主要業務フローを実施 |
| **移行時間** | 移行処理が許容時間内に完了するか | 全件移行の所要時間がダウンタイム許容内か |
| **差分移行** | 本番直前の差分データが正しく移行されるか | カットオーバー直前の差分移行リハーサル |

### 5.12 運用手順・移行リハーサル

| 観点 | 確認内容 | 確認方法 |
| :--- | :--- | :--- |
| **本番移行手順書の妥当性** | 本番移行手順書通りに作業を実施できるか | リハーサルで手順書を使って実際に作業 |
| **所要時間** | 移行作業が想定時間内に完了するか | リハーサルで実際の所要時間を計測 |
| **切り戻し手順** | 移行失敗時の切り戻し（ロールバック）手順が機能するか | 意図的に移行失敗を再現し、切り戻しを実施 |
| **運用マニュアルの妥当性** | 運用マニュアル通りにシステム操作・監視ができるか | 担当者がマニュアルのみを見て操作を実施できるか |
| **定期メンテナンス作業** | バッチ実行・ログ確認・バックアップ確認等の日常作業が手順書通りに実施できるか | 手順書に沿って日次・月次作業を実施 |

## 6. 工程横断で意識すべき観点

### 6.1 日本語・文字コード関連

日本語を扱うシステムで特有の問題が発生しやすい観点。全工程で意識する。

| 観点 | 確認内容 | 具体例 |
| :--- | :--- | :--- |
| **機種依存文字** | 機種依存文字（①②・㈱・㍉等）の登録・表示が正しく動作するか | 会社名に `㈱` を含む場合の登録・表示・CSV出力 |
| **絵文字（Unicode4バイト文字）** | 絵文字を含む文字列の登録・表示が正しく動作するか | 氏名・コメントフィールドに絵文字を入力した場合 |
| **半角・全角の混在** | 半角カタカナ・全角英数字の扱いが仕様通りか | 半角カタカナを入力した場合にエラーか全角変換されるか |
| **改行コードの扱い** | テキストエリアの改行コードが正しく処理されるか | 入力した改行が保存・表示で正しく扱われるか |
| **長音符・濁点の正規化** | 「ー」「が」など文字の正規化が行われているか（検索精度に影響）| 「ガ」と「ガ」（合成文字）が同一として検索されるか |

### 6.2 ブラウザのキャッシュ・Cookie

| 観点 | 確認内容 | 具体例 |
| :--- | :--- | :--- |
| **キャッシュによる旧データ表示** | 更新・削除後に古いデータがキャッシュされて表示されないか | 更新後にブラウザの「戻る」→「更新」で最新データが表示されるか |
| **Cookie の有効期限** | Cookieの有効期限が仕様通りに設定されているか | 「ログイン状態を保持する」のCookieが翌日も有効か |
| **Cookie のSecure・HttpOnly属性** | Secure（HTTPS）・HttpOnly属性が設定されているか | 開発者ツールでCookieの属性を確認 |

### 6.3 タイムゾーン・日付処理

| 観点 | 確認内容 | 具体例 |
| :--- | :--- | :--- |
| **日付・時刻のタイムゾーン** | サーバー・DB・クライアントのタイムゾーンが統一されているか | DBがUTCで保存 → 画面表示がJSTで正しく変換されるか |
| **年またぎ処理** | 12月31日から1月1日をまたぐ処理が正しく動作するか | 12月31日の翌日が1月1日（翌年）として処理されるか |
| **うるう年** | 2月28日・29日・3月1日の処理が正しいか | 2月28日の翌日がうるう年は29日・非うるう年は3月1日か |
| **月末日** | 月末日が月によって異なることへの対応が正しいか | 1月31日の翌月同日 → 2月は28日（または29日）として処理 |

### A. テスト観点チェックリスト（単体テスト）

設計したテストケースが以下の観点をカバーしているか確認する。

- [ ] 正常入力値での期待出力を確認している

### E. 用語集

| 用語 | 説明 |
| :--- | :--- |
| **テスト観点** | 何を確認するか、どの側面を検証するかという視点 |
| **テストケース** | 観点を実際のテスト手順・期待結果として具体化したもの |
| **カバレッジ** | テストがカバーしている範囲の割合。行・分岐・条件等の観点がある |
| **同値クラス分割** | 同じ動作をする入力値のグループに分けてテスト設計する手法 |
| **境界値分析** | 上限・下限・境界付近の値を重点的にテストする手法 |
| **デシジョンテーブル** | 条件と動作の組み合わせを表形式で整理するテスト設計手法 |
| **デグレード** | バグ修正・変更により正常動作していた機能が壊れること |
| **べき等性** | 同じ操作を複数回実行しても同じ結果になる性質 |
| **楽観的ロック** | 更新時にバージョン番号等で競合を検知する排他制御方式 |
| **OWASP Top 10** | Webアプリケーションの主要な脆弱性トップ10。セキュリティテストの基準 |
| **XSS** | クロスサイトスクリプティング。悪意あるスクリプトを埋め込む攻撃 |
| **SQLインジェクション** | SQL文に不正な値を埋め込みDBを不正操作する攻撃 |
| **CSRF** | クロスサイトリクエストフォージェリ。ユーザーを騙して不正なリクエストを送らせる攻撃 |
| **RTO** | Recovery Time Objective（目標復旧時間）。障害発生からシステム復旧までの目標時間 |
| **スタブ** | 未完成または外部のコンポーネントの代わりに応答する模擬モジュール |
