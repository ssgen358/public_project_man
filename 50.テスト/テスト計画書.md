## 1. テスト戦略・方針

### 1.1 テストの目的

本計画書は、システムが要件・設計を正しく実装し、定めた品質基準を満たしていることを確認するためのテスト活動を計画・管理することを目的とする。

### 1.2 テスト方針

| 方針 | 内容 |
| :--- | :--- |
| **シフトレフト** | 欠陥は早期工程で発見・修正するほどコストが低い。単体テスト・コードレビューを徹底する |
| **リスクベーステスト** | 限られた時間を最大活用するため、リスクの高い機能（重要業務・複雑ロジック）を優先してテストする |
| **自動化優先** | 回帰テストは自動化し、品質を維持しながらリリースサイクルを短縮する |
| **独立性の確保** | 開発者が自身のコードを単体テストし、別担当者が結合・総合テストを実施する |
| **エビデンス取得** | 全テストケースの実施結果とスクリーンショット等のエビデンスを保管する |

### 1.3 テストスコープ

| スコープ | 対象 | 対象外 |
| :--- | :--- | :--- |
| **機能テスト** | システムの全機能 | OS・ミドルウェア・外部パッケージの内部テスト |
| **性能テスト** | 主要業務トランザクション（TPS定義分） | 全機能の性能テスト |
| **セキュリティ** | OWASPトップ10に対応するリスク項目 | 物理セキュリティ |
| **データ移行** | 過去Xヶ月分の本番データ移行 | 対象外データのアーカイブ確認 |
| **環境テスト** | 動作保証ブラウザ・OS | 保証外ブラウザの詳細動作確認 |

### 1.4 品質管理の基本思想（ISO 9001 / TQM / QC）

システム開発のテスト活動は、製造業で長年実践されてきた品質管理手法の考え方を取り入れることで、属人化を防ぎ継続的に改善できる品質保証体制を構築できる。本プロジェクトでは以下の品質管理思想をテスト活動に組み込む。

#### 1.4.1 PDCAサイクルによるテスト管理

**PDCA（Plan-Do-Check-Act）サイクル**はデミングが提唱し、日本のQC活動で広く普及した継続的改善の枠組みである。テスト工程全体をPDCAとして捉え、単なる「バグ発見活動」にとどまらない品質向上の仕組みとする。

```mermaid
graph LR
    P["Plan（計画）<br>テスト計画策定<br>観点・リスク分析<br>品質目標設定"] --> D["Do（実施）<br>テストケース設計<br>テスト実行<br>バグ記録"]
    D --> C["Check（確認）<br>品質指標の計測<br>バグ傾向分析<br>目標との差異確認"]
    C --> A["Act（改善）<br>根本原因対策<br>是正処置実施<br>次工程への反映"]
    A --> P
```

| テスト活動 | PDCA | 主な内容 |
| :--- | :---: | :--- |
| テスト計画 | **P** | テスト観点洗い出し・リスク分析・品質目標設定・スケジュール策定 |
| テスト設計・実施 | **D** | テストケース作成・テスト実行・バグ起票・エビデンス取得 |
| 品質分析・確認 | **C** | バグ密度計測・パレート分析・テスト進捗確認・品質目標との差異評価 |
| プロセス改善 | **A** | バグ根本原因への対策・テストプロセスの改善・次フェーズへの知見反映 |

#### 1.4.2 ISO 9001 の原則をテストに適用

ISO 9001（品質マネジメントシステム）の7原則のうち、テスト活動に特に関連する原則を以下のように適用する。

| ISO 9001 の原則 | テスト活動への適用 |
| :--- | :--- |
| **顧客重視** | テストはユーザーが実際に使える品質を保証するために行う。テスト完了基準・品質目標はユーザー要件から導く |
| **プロセスアプローチ** | テスト設計→実施→報告を標準化されたプロセスとして管理し、担当者が変わっても品質が安定するようにする |
| **証拠に基づく意思決定** | バグ件数・密度・カバレッジ等の客観的データで品質を評価する。「感覚的に大丈夫そう」でリリース判断をしない |
| **継続的改善** | テスト後の振り返りをプロセスに組み込み、次フェーズ・次プロジェクトで品質水準を向上させる |
| **関係性管理** | 開発チーム・ユーザー・PMOが品質目標を共有し、協調して品質活動を行う |

> [!TIP]
> ISO 9001の「証拠に基づく意思決定」は、製造業では計測データや検査記録が根拠となる。システムテストでは、バグ密度・テスト合格率・カバレッジレポートがその証拠に相当する。「なんとなく品質が良さそう」という言葉ではなく、数値と証跡で品質を語る文化を育てることが重要。

#### 1.4.3 TQM（総合的品質管理）の考え方

**TQM（Total Quality Management：総合的品質管理）**は、品質をQA担当だけが担うのではなく、プロジェクト全員が関わるという思想を根幹に持つ。製造業では生産ラインに関わる全作業者が品質に責任を持つ考え方として定着している。

| TQM の考え方 | システム開発テストへの適用 |
| :--- | :--- |
| **品質は作り込む**（検査で発見するのではなく、前工程で品質を確保する） | コードレビュー・TDD・ペアプログラミングで製造段階から品質を作り込む。テストは「作り込まれた品質」の最終確認として機能させる |
| **全員参加**（品質はQA専任者だけのものではない） | 開発者が単体テストを書き、PLがレビューし、PMOが指標を管理する。テストへの参加を各担当者の責任として定義する |
| **源流管理**（問題を発生源で止める） | 不具合は下流工程に流さず、発生した工程で対処する（シフトレフト思想）。単体テストで発見したバグを結合テストに持ち込まない |
| **再発防止**（修正で終わりにしない） | バグ修正後に根本原因を分析し、同種のバグが再発しない仕組みを作る（是正処置） |
| **見える化**（データで現場の状態を把握する） | バグ密度・信頼度成長曲線・カバレッジを週次で可視化し、品質状態を全員が共有できる状態にする |

> [!NOTE]
> 製造業の「ゼロディフェクト（ZD）運動」はIT開発では「バグゼロ文化の醸成」に、「QCサークル活動」は「定期的な品質振り返りミーティング」に対応する概念として理解できる。製造現場の手法をそのまま持ち込むのではなく、「なぜその手法が効果的なのか」という本質を理解した上でシステム開発に転用することが重要。

## 2. テスト種別と実施内容

### 2.1 テスト種別の全体像

```mermaid
graph LR
    UT[単体テスト<br/>Unit Test] --> IT[結合テスト<br/>Integration Test]
    IT --> ST[総合テスト<br/>System Test]
    ST --> UAT[受入テスト<br/>UAT]

    subgraph 開発側
        UT
        IT
    end
    subgraph QA/PMO
        ST
    end
    subgraph ユーザー
        UAT
    end
```

### 2.2 単体テスト（Unit Test / UT）

**目的**: 関数・モジュール単位の動作確認。欠陥の早期発見と実装品質の担保。

| 項目 | 内容 |
| :--- | :--- |
| **実施主体** | 開発担当者（自己テスト） |
| **対象** | 全実装モジュール |
| **使用ツール** | JUnit（Java）/ Pytest（Python）/ Jest（JS）等 |
| **カバレッジ目標** | 行カバレッジ80%以上（クリティカル機能：90%以上） |
| **完了基準** | 全テストケースがパスし、カバレッジ目標を達成 |
| **成果物** | 単体テスト仕様書・テスト成績書・カバレッジレポート |

**テスト観点**:
- 正常系（正常な入力値での動作確認）
- 異常系（不正入力・NULL・境界値での動作確認）
- 境界値（最大値・最小値・閾値でのテスト）

### 2.3 結合テスト（Integration Test / IT）

**目的**: モジュール間・機能間の連携動作確認。インターフェース不整合の検出。

| 項目 | 内容 |
| :--- | :--- |
| **実施主体** | PL・開発担当者（別担当者によるクロステスト推奨） |
| **対象** | 機能間・システム間インターフェース |
| **テスト区分** | 機能内結合テスト（FIT）→ 機能間結合テスト（SIT） |
| **完了基準** | テスト実施率100%、S/Aランクバグ0件 |
| **成果物** | 結合テスト仕様書・テスト成績書・バグ管理表 |

**テスト観点**:
- 画面→業務ロジック→DBの一連の処理フロー
- 外部API・外部システムとのインターフェース
- バッチ処理の連携・順序
- データ整合性（複数テーブルにまたがる処理）

### 2.4 総合テスト（System Test / ST）

**目的**: システム全体として要件・非機能要件を満たすかの確認。

| 項目 | 内容 |
| :--- | :--- |
| **実施主体** | PMO・QA担当者（開発チームと独立した担当者） |
| **対象** | システム全体（機能・非機能） |
| **テスト区分** | 機能テスト・性能テスト・セキュリティテスト・回帰テスト |
| **完了基準** | テスト実施率100%、S/Aランクバグ0件、性能目標値達成 |
| **成果物** | 総合テスト仕様書・テスト成績書・性能テストレポート・セキュリティテストレポート |

**テスト種類**:

| テスト種類 | 目的 | 実施タイミング |
| :--- | :--- | :--- |
| 機能テスト | 全機能要件の充足確認 | ST開始〜 |
| 業務シナリオテスト | エンドツーエンドの業務フロー確認 | ST中盤〜 |
| 回帰テスト | バグ修正後に既存機能への影響がないことを確認 | バグ修正後 |
| 性能テスト | 応答時間・スループット・リソース使用率の確認 | ST後半 |
| セキュリティテスト | 脆弱性・認可制御の確認 | ST後半 |
| 移行テスト（リハーサル） | 本番移行手順の検証 | ST完了後 |

### 2.5 受入テスト（User Acceptance Test / UAT）

**目的**: ユーザー視点でシステムが業務要件を満たし、実際に使えることを確認する。

| 項目 | 内容 |
| :--- | :--- |
| **実施主体** | ユーザー部門（業務担当者） |
| **支援** | PMO・開発チームがサポート役として参加 |
| **対象** | 業務シナリオ・ユーザーストーリー |
| **テスト方法** | 実業務に近いシナリオベースのテスト |
| **完了基準** | ユーザーが受入可否を判定・署名 |
| **成果物** | UATシナリオ書・テスト成績書・受入完了報告書 |

**UAT実施の注意事項**:
- テストシナリオはユーザーが実際に行う業務手順を元に作成する
- テスト期間中は開発チームのサポートデスクを設置する
- 重大な不具合が発見された場合の判断プロセスを事前に合意する
- 本番に近いデータを使用する（個人情報は匿名化・マスキング）

### 2.6 非機能テスト

#### 2.6.1 性能テスト

| テスト種類 | 目的 | 測定指標 |
| :--- | :--- | :--- |
| **負荷テスト（Load Test）** | 想定同時接続数での動作確認 | レスポンスタイム・エラーレート |
| **スパイクテスト（Spike Test）** | 急激な負荷上昇への耐性確認 | 応答時間変化・リカバリ時間 |
| **耐久テスト（Soak Test）** | 長時間稼働時のメモリリークなど確認 | メモリ・CPUの推移 |
| **限界テスト（Stress Test）** | システムの限界値・障害点の特定 | 破綻する負荷の閾値 |

**性能目標例**:

| 指標 | 目標値 | 測定条件 |
| :--- | :--- | :--- |
| レスポンスタイム（平均） | 1秒以内 | 通常時（同時50ユーザー） |
| レスポンスタイム（95%ile） | 3秒以内 | 同上 |
| スループット | ○○TPS以上 | ピーク時（同時100ユーザー） |
| エラーレート | 0.1%以下 | 上記条件下 |
| CPU使用率 | ピーク時80%以下 | 上記条件下 |

#### 2.6.2 セキュリティテスト

| テスト項目 | 対象 | テスト方法 |
| :--- | :--- | :--- |
| **認証・認可テスト** | ログイン機能・アクセス制御 | 権限のないリソースへのアクセス試行 |
| **SQLインジェクション** | 入力フォーム・クエリパラメータ | OWASP ZAP / 手動テスト |
| **XSS（クロスサイトスクリプティング）** | 入力フォーム・表示箇所 | OWASP ZAP / 手動テスト |
| **CSRFテスト** | フォーム送信機能 | トークン検証確認 |
| **セッション管理** | セッション有効期限・固定化 | 手動テスト |
| **脆弱性スキャン** | 使用ライブラリ・ミドルウェア | OWASP Dependency-Check / Snyk |

## 3. テスト環境

### 3.1 環境構成

| 環境 | 用途 | 管理担当 | 備考 |
| :--- | :--- | :--- | :--- |
| **開発環境（DEV）** | 開発・単体テスト | 開発担当者 | 個人PC or 開発サーバー |
| **結合テスト環境（IT）** | 結合テスト | PL | 本番に近い構成 |
| **総合テスト環境（ST）** | 総合テスト・UAT準備 | PMO | 本番同等構成 |
| **UAT環境** | UAT（受入テスト） | PMO/ユーザー | 本番同等構成 |
| **本番環境（PROD）** | 本番稼働 | 運用担当 | 移行リハーサル後に使用 |

### 3.2 環境管理ルール

- **データ管理**: テスト環境には本番データを直接使用しない。匿名化・マスキングしたデータを使用する
- **環境差分管理**: 環境間の差分（設定値・ミドルウェアバージョン等）を管理表で管理する
- **環境リセット**: 各テストフェーズ開始前に環境をクリーンな状態にリセットする手順を整備する
- **アクセス管理**: 本番環境へのアクセスは最小権限の原則に従い、開発担当者のアクセスを制限する

### 3.3 動作保証環境（ブラウザ・OS）

| カテゴリ | 保証環境 | 備考 |
| :--- | :--- | :--- |
| **Webブラウザ** | Google Chrome（最新版）、Microsoft Edge（最新版） | IE/旧ブラウザは対象外 |
| **OS（クライアント）** | Windows 11、Windows 10 | macOS: 別途要確認 |
| **OS（サーバー）** | Amazon Linux 2 / Ubuntu 22.04 LTS | プロジェクト方針による |
| **画面解像度** | 1920×1080以上 | 1280×720でも表示崩れないこと |
| **モバイル** | 別途定義（対応する場合） | |

## 4. テストスケジュール

### 4.1 テストフェーズとスケジュール概要

| フェーズ | 期間 | 主な作業 |
| :--- | :--- | :--- |

| **UAT** | ST完了後 〇週間 | ユーザー受入テスト |
| **移行リハーサル** | UAT期間中 | 本番移行手順の検証 |

### 4.2 日次テスト管理サイクル

| タイミング | 作業 | 担当 |
| :--- | :--- | :--- |
| 朝会（9:30-9:45） | テスト進捗確認・ブロッカー報告 | テストリード |
| 終業前（17:30） | テスト実績をツールへ入力 | テスト担当者 |
| 日次 | バグ状況集計・テスト進捗更新 | PMO |
| 週次 | 品質レポート作成・会議体報告 | PMO |

## 5. テスト設計・実施プロセス

### 5.1 テストケース作成プロセス

```mermaid
graph TD
    Req[要件定義書/設計書] --> Analysis[テスト観点分析]
    Analysis --> Condition[テスト条件抽出]
    Condition --> Case[テストケース作成]
    Case --> Review[テストケースレビュー]
    Review --> Fix{指摘あり?}
    Fix -- Yes --> Case
    Fix -- No --> Register[テスト管理ツールへ登録]
    Register --> Execute[テスト実施]
```

### 5.2 テストケース作成の観点

**機能テストの観点**:

| 観点 | 内容 | 例 |
| :--- | :--- | :--- |
| **正常系** | 正常な入力・操作での動作確認 | 正しいデータで受注登録が成功する |
| **異常系** | 不正な入力・操作でのエラー処理確認 | 必須入力を空白のまま送信 → エラーメッセージが表示される |
| **境界値** | 最大値・最小値・閾値付近のテスト | 文字数: 0文字、99文字、100文字（上限）、101文字 |
| **権限** | ユーザー権限に応じた表示・操作制御 | 閲覧権限のみのユーザーは編集ボタンが表示されない |
| **業務シナリオ** | 実業務のエンドツーエンドフロー | 受注→在庫引当→出荷→請求の一連操作 |

### 5.3 テストケーステンプレート

| 項目 | 内容 |
| :--- | :--- |
| **テストケースID** | TC-XXXX（一意の識別子） |
| **テスト対象機能** | 対象となる機能名・画面名 |
| **テスト観点** | 正常系 / 異常系 / 境界値 / 権限 / シナリオ |
| **テスト条件** | テスト実施に必要な前提条件・テストデータ |
| **操作手順** | テストの実施手順（ステップバイステップ） |
| **期待結果** | 正しい動作・表示内容 |
| **実際の結果** | テスト実施後の実際の動作（実施後に記載） |
| **合否** | Pass / Fail / N/A |
| **バグID** | Failの場合、関連するバグのID |
| **実施日・実施者** | テスト実施の日付と担当者 |

### 5.4 テストケース例

| TC-ID | 対象機能 | 観点 | 条件 | 操作手順 | 期待結果 | 合否 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| TC-001 | 受注登録 | 正常系 | ログイン済み、在庫あり | ①商品を選択 ②数量を入力 ③登録ボタンをクリック | 受注が登録され「登録完了」メッセージが表示される | Pass |

### 6.1 バグ管理プロセス

### 6.3 バグ対応SLA

| :--- | :--- | :--- | :--- |

| **C（Minor）** | 週次トリアージで判断 | 計画対応 | 次フェーズ以降で検討可 |

### 6.4 バグ発生時の対応フロー（ST/UAT中の重大バグ）

```mermaid
graph TD
    Bug[S/Aランクバグ発見] --> PMO[PMOへ即時報告]
    PMO --> PM[PMへ報告]
    PM --> Decision{スケジュール影響を評価}
    Decision -->|影響大| Escalate[オーナーへエスカレーション]

    Escalate --> Fix
    Fix --> Verify[影響範囲の回帰テスト実施]
    Verify --> Report[バグ解決報告]
```

### 6.5 QC手法によるバグ分析・品質改善

製造業で使われる**QC 7つ道具**をバグ分析に活用する。感覚ではなくデータでバグのパターンを可視化することで、効果的な品質改善策の立案が可能になる。

#### 6.5.1 パレート分析（Pareto Chart）

バグを種別・機能・原因などで分類し、件数の多い順に並べて分析する。「全バグの80%は20%の原因から生まれる」という**パレートの法則（80/20法則）**に基づき、重点対策箇所を特定する。

| 分析軸 | 活用目的 |
| :--- | :--- |
| **バグ発見機能別** | どの機能にバグが集中しているかを把握し、重点テストを計画する |
| **バグ原因分類別** | 実装ミス・仕様誤解・設計漏れなど原因の割合を把握し、再発防止策を立案する |
| **バグ深刻度別** | S/A/B/C各ランクの分布状況を把握し、対応優先順位の妥当性を確認する |
| **発見フェーズ別** | 単体テスト・結合テスト・総合テスト・UATのどのフェーズで多く発見されたかを把握する |

> [!TIP]
> パレート分析はExcelで手軽に作成できる。週次品質レポートにパレート図を追加すると、バグのパターンが視覚的に明確になりマネジメント層への報告も容易になる。「実装ミスとUI表示の2原因で全バグの75%を占める」といった具体的な数字で品質状況を語れるようにすることが目標。

#### 6.5.2 特性要因図（フィッシュボーン図）によるバグ根本原因分析

バグの根本原因を系統的に可視化するための図。品質工学の父・石川馨が開発した手法（石川ダイアグラム）で、結果（バグ）に対する要因を整理する。

製造業の**「4M（Man・Machine・Method・Material）」**をシステム開発に転用した枠組みで根本原因を分類する。

| 製造業の要因軸 | IT開発への転用 | バグ原因の例 |
| :--- | :--- | :--- |
| **Man（人）** | 開発者・テスター | スキル不足・仕様誤解・疲労・コミュニケーション不足 |
| **Machine（機械）** | 開発環境・ツール | IDE・テスト環境の差分・フレームワークの不具合 |
| **Method（方法）** | 開発プロセス | レビュー不足・テスト観点の欠如・ドキュメント不備 |
| **Material（材料）** | 要件・設計書 | 要件の曖昧さ・設計書の矛盾・仕様変更の未反映 |
| **Environment（環境）** | 開発・テスト環境 | 環境差分・テストデータ不整合・外部システム起因 |

**活用場面**:
- 同種のバグが繰り返し発生する場合
- S/Aランクの重大バグが発生した場合
- テストフェーズ終了後の振り返り（品質総括）

> [!TIP]
> 特性要因図は「実装ミス」で原因を止めてはいけない。「なぜ実装ミスが起きたか？」「なぜレビューで発見できなかったか？」と深掘りすることで、本当の改善策が見えてくる。「気をつける」「注意する」を対策にしても再発を防ぐことはできない。

#### 6.5.3 管理図（Control Chart）によるバグトレンド監視

テストフェーズを通じてバグ発見数の推移を管理図的に監視する。バグの収束傾向を可視化し、リリース判定の客観的根拠とする。

**バグ収束の判断指標**:

| 指標 | 計算方法 | 収束の目安 |
| :--- | :--- | :--- |
| **週次新規バグ発生率** | 当週新規バグ数 ÷ 全バグ数 × 100 | 最終週で5%以下 |
| **バグ修正完了率** | 修正完了バグ数 ÷ 全発見バグ数 × 100 | 95%以上（S/Aは100%） |
| **再発生率（再オープン率）** | 再オープンバグ数 ÷ 修正完了バグ数 × 100 | 5%以下 |
| **累積バグ発見数の増加率** | （当週累計 - 前週累計）÷ 前週累計 × 100 | 最終週で10%未満 |

> [!WARNING]
> バグ発見数が突然「ゼロ」になった場合は、品質向上ではなくテストが形骸化している可能性を疑う。信頼度成長曲線（バグ累積発見数のS字カーブ）で正常な収束パターンを確認することが重要。急激な収束はテスト実施が手抜きになっているサインの場合がある。

#### 6.5.4 層別（Stratification）によるバグ分類分析

バグデータを複数の視点で層別（グループ分け）し傾向を分析することで、対策の焦点を絞る。

| 層別の軸 | 分析で得られる洞察 |
| :--- | :--- |
| **発見フェーズ別** | どのフェーズで多くバグが見つかるかを把握し、源流工程（設計・製造）の品質を評価する |
| **機能・画面別** | バグが集中している機能を特定し、テストリソースと開発リソースを重点配分する |
| **原因分類別** | 実装ミス・仕様誤解・設計漏れ等の割合を把握し、最も効果的な再発防止策を立案する |
| **再発有無** | 過去に修正したバグが再発しているかを追跡し、是正処置の有効性を評価する |

> [!NOTE]
> 担当者別の層別分析は個人の能力評価ではなく、「どのスキルを補強すべきか」「ペアレビューが必要か」というプロセス改善の判断材料として活用する。バグデータを個人評価に直結させると、バグを隠蔽する文化が生まれるリスクがある。

### 6.6 根本原因分析と是正処置・予防処置（CAPA）

**CAPA（Corrective and Preventive Action：是正処置・予防処置）**は、ISO 9001 が要求する品質改善の核となるプロセスである。製造業では工程不良に対して必ず実施されるが、システム開発のバグ管理にも同様に適用できる。

```mermaid
graph TD
    Bug[バグ発見・修正] --> Check{重大バグか？<br>同種バグが繰り返すか？}
    Check -- No --> Close[バグクローズ]
    Check -- Yes --> RCA[根本原因分析<br>なぜなぜ分析<br>特性要因図]
    RCA --> CA[是正処置<br>再発防止策の実施<br>プロセス・チェックリスト改善]
    CA --> PA[予防処置<br>類似箇所への先手対策<br>テストケース拡充]
    PA --> Monitor[効果確認<br>次フェーズで再発がないか確認]
    Monitor --> Lessons[ナレッジ化<br>テスト観点・チェックリストへ反映]
```

**なぜなぜ分析（5 Whys）の実施例**:

S/Aランクのバグや同種の繰り返しバグに対してなぜなぜ分析を実施し、表面的な原因ではなく根本原因まで掘り下げる。

| 段階 | 問いと答え |
| :--- | :--- |
| **事象** | 総合テストで料金計算バグが発覚した |
| **なぜ1** | なぜバグが発生したか？ → 消費税の端数処理（切り捨て/四捨五入）の仕様が実装と異なっていたから |
| **なぜ2** | なぜ仕様と異なる実装になったか？ → 設計書に端数処理の仕様が明記されていなかったから |
| **なぜ3** | なぜ設計書に明記されなかったか？ → 設計書のレビューチェックリストに「計算の端数処理確認」が含まれていなかったから |
| **なぜ4** | なぜチェックリストになかったか？ → 過去の経験が設計レビュープロセスに還元される仕組みがなかったから |
| **根本原因** | 過去の知見を標準プロセスに組み込む仕組みがない |
| **是正処置** | 設計レビューチェックリストに「計算ロジック・端数処理の明記確認」を追加する |
| **予防処置** | テスト観点一覧に「計算精度の境界値テスト」を明示的に追記し、全計算処理で漏れなく確認できるようにする |

**是正処置・予防処置の使い分け**:

| 処置の種類 | 定義 | 例 |
| :--- | :--- | :--- |
| **是正処置（Corrective Action）** | 発生した問題の根本原因を除去し、再発を防ぐ措置 | レビューチェックリストへの端数処理確認項目の追加 |
| **予防処置（Preventive Action）** | まだ発生していないが発生しうる問題を事前に防ぐ措置 | 類似する計算処理全般のテストケース拡充・他機能の確認 |

> [!TIP]
> 「是正処置」と「バグ修正」は別物。バグ修正は「今回の問題を直す」ことだが、是正処置は「同じ原因で次も起きないようにする」こと。「なぜなぜ分析」で根本原因まで掘り下げた上で対策を打つのが是正処置の本質であり、「気をつける」「注意する」は是正処置の対策として認めない。

### B. 業務シナリオテストのシナリオ例

#### B.1 受注〜出荷の業務シナリオ

```
【シナリオ概要】
新規の受注から在庫引当→出荷指示→出荷完了までの一連の業務フローを確認する。

【前提条件】
- 商品Aの在庫：10個
- 営業担当者権限でログイン

【手順】
1. 受注管理画面から新規受注を入力する（商品A: 3個）
2. 受注登録後、在庫が7個に減少していることを確認する
3. 出荷管理画面で当該受注の出荷指示を行う
4. 出荷完了登録を行う
5. 受注明細の状態が「出荷完了」になっていることを確認する
6. 請求管理画面で請求データが生成されていることを確認する

【確認ポイント】
- 各画面での在庫数の整合性
- 受注ステータスの遷移（受注受付→引当済み→出荷完了）
- 帳票（納品書）の出力内容
```
